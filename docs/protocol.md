# Протокол и границы поддержки

[README](../README.md) · [Внедрение](integration.md) · [Диагностика](diagnostics.md)

Этот документ описывает реализованный профиль и результаты разбора исходников
и реального обмена. Он не является универсальной спецификацией всех станций SFR.
Код формирования и разбора пакетов: [`SfrProtocol.cs`](../SfrConnect/SfrProtocol.cs).

## USB HID

Текущий профиль: Windows, VID `2047`, PID `0301`, Report ID `3F`, отчёт 64 байта.
При открытии проверяется выходной отчёт в HID-дескрипторе. В HidSharp первый
байт буфера уже содержит Report ID: дополнительный нулевой байт перед `3F` не нужен.

Общий вид: `3F <длина> FD <команда и данные> <CS> FE`, затем заполнение до
64 байт. Длина включает байты от `FD` до `FE`. Исходящий хвост заполняется нулями.
Входящий хвост за объявленной длиной может содержать произвольные старые данные:
они видны в журнале, но не являются частью ответа.

Контрольная сумма запроса — сумма байтов команды и данных с переносом старшего
байта в младший. В наблюдавшихся ответах поле CS равно нулю и не соответствует
такой сумме. Сейчас CS ответов не проверяется; проверяются длина, Report ID,
границы, команда, адрес и допустимость данных. Это ограничение текущего профиля.

| Операция | Значащая часть отчёта |
|---|---|
| Читать ячейку 01 | `3F 05 FD 01 01 02 FE` |
| Читать ячейку 03 | `3F 05 FD 01 03 04 FE` |
| Ответ чтения | `3F 09 FD 01 <ячейка> <4 байта данных> <CS> FE` |
| Записать ячейку 03 | `3F 09 FD 02 03 b0 b1 b2 b3 CS FE` |
| Сигнал | `3F 05 FD 03 01 04 FE` |

Для сигнала ответ не ожидается; после отправки выдерживается 300 мс под
блокировкой обмена. Успешная отправка не доказывает, что звук физически прозвучал.
Тайм-аут записи HID — 2000 мс, чтения — 1000 мс.

| Ответ | Использование в DLL |
|---|---|
| `2A 06` | Чип недоступен для чтения; один такой ответ не определяет размер памяти |
| `2A 55` | Подтверждение команды записи, после которого всё равно проверяются данные |
| `2A 08` | Наблюдался при записи; точная расшифровка не подтверждена. Выполняется чтение для проверки, повторной отправки записи нет |

Например, полный значащий ответ отсутствия: `3F 05 FD 2A 06 00 FE`.
Остальные ответы не объявляются автоматически отсутствием чипа. В протоколе
нет используемого DLL номера транзакции; после тайм-аута нельзя считать поздний
ответ ответом на следующую команду. Поэтому ошибки обмена могут требовать
закрытия потока, в отличие от штатного ответа о недоступности чипа.

## Память и номер

Адреса ниже шестнадцатеричные; ячейка содержит четыре байта.

| Ячейка | Использование |
|---|---|
| `00` | DLL не изменяет |
| `01` | Маркер; при очистке записывается текущее местное время `00 HH mm ss` в BCD |
| `02` | Обнуляется при очистке |
| `03` | Номер чипа |
| `04` | Заголовок/счётчик или служебный режим; после очистки `05 00 00 00` |
| `05–7F` | Область отметок в поддерживаемом профиле; обнуляется при очистке |

Чтение номера: `b0 + b1 × 200 + b2 × 40000`; первые три байта должны быть меньше
200. Четвёртый байт в декодировании номера не участвует. Номер 0 допустим.

Запись нового номера повторяет формат изученных приложений:
`[number % 200, number / 200, 0, 0]`, допустимо **0–39999**.
При записи номера без очистки у обычного чипа меняются только эти четыре байта
ячейки 03. При отдельной очистке обычного чипа вся ячейка номера сохраняется.

Ячейка 01 читается по границам операций для обнаружения изменения данных.
Это **не UID**: два чипа могут иметь одинаковый маркер. Во время операции нужен
один и тот же чип; DLL не гарантирует обнаружение подмены на чип с совпавшими полями.

На проверенной станции читались 18000, 20000 и 39999. После записи 40000 внешним
приложением наблюдался `2A 06`, а возврат к 39999 восстановил чтение. Причина
этого поведения не установлена; из наблюдения нельзя вывести общий предел
аппаратного формата. Ограничение новых номеров в API задано явно.

## Определение служебного чипа

Ячейка 04 проверяется перед изменением. Формат участника: первый байт не меньше
5, второй байт нулевой. Третий и четвёртый не обязаны быть нулевыми:
в реальном журнале прочитан `06 00 F0 00`. В SFR phone (`ServiseNfc.zadanie`,
ветка `idV == 4`) проверяется только второй байт, затем первый используется как
граница чтения. SFR basic и SportOrg также используют первый байт как счётчик,
не требуя нулевого хвоста. Назначение дополнительных байтов здесь не установлено;
при записи только номера DLL их сохраняет. Известные служебные значения:

- `00 01 00 00`, `03 03 03 03`, `05 05 05 05`;
- `01 02 00 00`, `02 02 00 00`, `03 02 00 00`, `05 02 00 00`, `09 02 00 00`;
- префиксы `01 09` и `02 09` с двумя дополнительными байтами.

Остальное считается `Unknown`. При `FormatUnknownCards = true` (по умолчанию)
такой чип при присвоении/очистке приводится к обычному формату с очисткой,
аналогично служебному. При `false` он не изменяется и возникает
`SfrProtectedCardException`. Служебный чип при присвоении или очистке всегда
переводится в обычный с очисткой. Сначала записывается и
проверяется заголовок `05 00 00 00`, затем стираются остальные служебные данные.
При отдельной очистке служебного/неизвестного чипа корректный номер 0–39999 сохраняется,
иначе устанавливается 0. При присвоении используется запрошенный номер.

## Алгоритм очистки

Реализация: [`SfrStation.Cards.cs`](../SfrConnect/SfrStation.Cards.cs).

1. Прочитать маркер, тип и номер. Проверить допустимость профиля и счётчика.
2. Прочитать весь поддерживаемый диапазон памяти для подготовки изменений,
   включая хвост за текущим счётчиком. Непустые ячейки 02 и 05–7F включить в план
   обнуления. Уже пустые ячейки не перезаписывать.
3. При временной недоступности во время подготовки ждать возврата в пределах
   настройки. После возврата сверить маркер и заголовок, отбросить частичный
   план и прочитать заново. Если подготовка не завершена, вернуть
   `PreparationFailed`: записей ещё не было. Недоступная ячейка сама по себе
   не вызывает вывод о неподдерживаемом размере памяти.
4. Выполнить план, проверяя маркер и заголовок перед каждой записью.
   У служебного/неизвестного чипа заголовок меняется первым. При необходимости изменить
   номер и сбросить заголовок участника; новый маркер времени записать последним.
5. По умолчанию (`AfterEachWrite`) сразу прочитать каждую записанную ячейку и
   сравнить данные до следующей записи. После `2A 08` или недоступности при
   чтении подтвердить также заголовок и маркер, при необходимости ожидая возврата.
   В остальных режимах после `2A 55` сразу читается только записанный заголовок;
   после `2A 08` текущая ячейка подтверждается до продолжения в любом режиме.
6. В режиме `AfterEachWrite` проверить номер, тип и маркер, без полного прохода
   памяти. В режиме `FullMemory` сначала прочитать весь диапазон 02–7F и
   сравнить с ожидаемым содержимым. При недоступности ждать возврата и повторять
   выбранную проверку целиком. Несовпадение данных завершает команду неуспехом.
7. Только после подтверждения вернуть успех; асинхронная команда также
   посылает сигнал и выдерживает паузу.

Это очистка памяти отметок, а не только сброс заголовка. Стартовая отметка
не создаётся. Подготовка по-прежнему читает весь диапазон, поэтому две физические
записи не означают два USB-запроса. Немедленная проверка убирает повторный полный
проход, но не обнаружит более позднее повреждение уже проверенных ячеек или
изменение ранее пустого хвоста. Для этого доступен `FullMemory`.

В дополнительном режиме `ThroughLastNonEmptyCell` подготовка остаётся полной,
а итоговый проход для обычного чипа ограничивается последней непустой ячейкой,
найденной при подготовке, минимум 05. Это не граница из ячейки 04: старые отметки
за счётчиком тоже находятся и стираются. При выборе этого режима служебные и
неизвестные чипы переключаются на `FullMemory`. Пустой хвост проверяется до записи,
но не после неё. Для последней непустой ячейки 06 экономится 121 запрос чтения
в итоговом проходе; это расчёт обменов, не измерение времени на станции.

Повторы касаются чтения; уже отправленная запись автоматически не повторяется.
Ожидание возврата по умолчанию 5000 мс с интервалом 200 мс, отдельно для
поддерживаемых фаз проверки. Частичное возвращение не продлевает текущий срок.
Сбои между записями и ошибки USB могут требовать переподключения:
точный контракт результата описан в [руководстве](integration.md).

Очистка не атомарна: после первой попытки изменения возможен частичный результат,
отката нет. Отмена после этой границы не прерывает проверку. Поддерживается
профиль 128 ячеек 00–7F; размер через NFC System Info по USB не определяется.
Очистка памяти за 7F не гарантируется, для других форматов нужен отдельный профиль.

## На чём основана реализация

- Драйвер SFR из SportOrg: HID-команды, чтение номера и пауза после сигнала.
- Опубликованные производителем [исходники SFR basic](https://sfr-system.ru/software/SFRbasic_source.exe),
  файлы `STFform.cpp` и `STFform.h`: команды, формат номера, память и служебные
  заголовки. Архив исследовался без запуска EXE.
- Предоставленный `SFRphone_1.4.8.apk`: в `StartFragment.writeToNfc` очистка
  передаёт в `ServiseNfc.zapisNum` размер памяти из `getKolBlok`, а не счётчик
  заголовка. `zapisNum` запрашивает чтение памяти и ищет последнюю непустую
  ячейку, затем формирует запись до этой границы (минимум 05). В
  `MyNfcListener.readBlocks` используются групповые NFC-чтения; при ошибке есть
  переход на одиночные чтения и поиск границы по содержимому. В режиме полной
  очистки `writeBloks` (`idV == 10`) также есть пропуск уже пустых ячеек.
  В DLL используется тот же принцип определения границы по содержимому;
  пропуск ненужных записей и итоговая проверка реализованы нашим USB-алгоритмом.
  Это не точная копия телефонного обмена: телефон использует NFC, определяет
  размер памяти и может читать несколько блоков за запрос. DLL по-прежнему
  работает с отдельными USB-запросами и профилем 128 ячеек.
- Предоставленный `base.apk` (SFR smart terminal 0.12.1): USB-запись каждой
  ячейки с немедленным чтением и сравнением, без отдельного полного прохода.
  Этот порядок используется в `AfterEachWrite`; поиск границы двоичным поиском
  и перезапись ячейки 00 не перенесены. Подробности — [анализ USB-приложений](usb-app-analysis.md).
- Журналы реальной станции, в том числе подтверждение записи `2 → 3`,
  ответы `2A 55`, `2A 08` и потеря чипа при чтении/записи.

Сохранённые ответы и имитация транспорта используются в
[`SfrConnect.Tests`](../SfrConnect.Tests). Они проверяют поведение DLL,
но не подтверждают совместимость с любой прошивкой или моделью станции.
