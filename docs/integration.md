# Внедрение SfrConnect

[README](../README.md) · [Диагностика](diagnostics.md) · [Протокол](protocol.md)

Для обычного приложения используйте `SfrNumberWriter.AssignAsync` и `ClearAsync`:
они ждут чип, выполняют действие, проверяют результат и подают сигнал. Приложение
отвечает за выбор станции, интерфейс, свою базу данных и жизненный цикл соединения.

## 1. Подключение к проекту

### Через исходный проект — предпочтительный вариант

В Visual Studio добавьте `SfrConnect/SfrConnect.csproj` в решение и добавьте
ссылку на него из приложения: «Зависимости → Добавить ссылку на проект».
NuGet-зависимость HidSharp будет перенесена автоматически.

Для существующего расположения `OrientCalculator/OrientCalculator/OrientCalculator.csproj`
рядом с репозиторием `SfrConnect` ссылка выглядит так:

```xml
<ItemGroup>
  <ProjectReference Include="..\..\SfrConnect\SfrConnect\SfrConnect.csproj" />
</ItemGroup>
```

Путь считается от файла `.csproj`, не от каталога решения. Саму ссылку в
OrientCalculator эта документация не добавляет. Его текущий WPF-проект
`net8.0-windows` совместим с библиотекой `net8.0`.

### Через готовую DLL

Соберите решение в Release. Из `SfrConnect.Diagnostics/bin/Release/net8.0/`
возьмите `SfrConnect.dll` и `HidSharp.dll`. Добавьте ссылки с копированием в
выходной каталог приложения; например, если оба файла находятся в `lib/`:

```xml
<ItemGroup>
  <Reference Include="SfrConnect">
    <HintPath>lib\SfrConnect.dll</HintPath>
    <Private>true</Private>
  </Reference>
  <Reference Include="HidSharp">
    <HintPath>lib\HidSharp.dll</HintPath>
    <Private>true</Private>
  </Reference>
</ItemGroup>
```

Приложению нужен совместимый .NET runtime. Для WPF с целевой платформой .NET 8
это .NET 8 Desktop Runtime, если приложение не опубликовано как self-contained.
Одна DLL не включает runtime. .NET Framework 4.x не может напрямую использовать
эту сборку. `regsvr32` и `DllImport` не нужны. Обновляйте библиотеку вместе с
пересборкой приложения: API пока развивается, двоичная совместимость отдельных
замен DLL между версиями не гарантируется.

## 2. Выбор станции и настройки

```csharp
using SfrConnect;

var devices = SfrStation.FindDevices();
foreach (var device in devices)
    Console.WriteLine($"{device.ProductName}: {device.DevicePath}");

if (devices.Count != 1)
    return; // Let the operator choose a DevicePath when several stations are connected.

using var station = SfrStation.Open(devices[0].DevicePath, options: new SfrStationOptions
{
    VerificationReturnTimeoutMs = 5000,
    VerificationRetryIntervalMs = 200
});
var writer = new SfrNumberWriter(station);
```

`FindDevices()` не отправляет команд. Не выбирайте первое устройство молча, если
их несколько. `DevicePath` может измениться после переподключения: тогда повторите
поиск. `FindDevices(includeOtherHidDevices: true)` предназначен для диагностики;
`Open` всё равно работает только с профилем SFR.

`Open` проверяет дескриптор и открывает HID-поток. Оно не читает чип и не подаёт
сигнал. Для GUI поиск и открытие выполняйте вне потока интерфейса.

| Настройка | По умолчанию | Значение |
|---|---:|---|
| `VerificationReturnTimeoutMs` | 5000 мс | Срок ожидания возврата после первого ответа о недоступности при поддерживаемой подготовке/проверке |
| `VerificationRetryIntervalMs` | 200 мс | Пауза между повторными чтениями |
| `FormatUnknownCards` | `true` | При присвоении/очистке приводить неизвестный заголовок к обычному формату с полной очисткой поддерживаемого диапазона, даже при `clearCard: false` |
| `ClearMode` | `SfrClearMode.AfterEachWrite` | Немедленная проверка каждой записи; доступны также `FullMemory` и `ThroughLastNonEmptyCell` с итоговым проходом памяти |

Настройки фиксируются при открытии соединения. Для изменения завершите текущую
операцию и откройте станцию заново. Нулевой срок отключает повторы; отрицательный
срок и неположительный интервал недопустимы.

Это **не общий тайм-аут команды**. Первоначальный поиск идёт каждые 250 мс после
завершения чтения и не ограничен по времени без `CancellationToken`.
Ожидание возврата применяется отдельно при подготовке очистки, проверке номера,
подтверждении записанной ячейки после `2A 08`, немедленной проверке после `2A 55`
и итоговой проверке очистки. В пределах одного такого ожидания повторное
исчезновение не начинает срок заново. Полная проверка после возврата может
закончиться позже срока ожидания. Тайм-аут HID-чтения — 1000 мс, записи — 2000 мс.

## 3. Чтение, присвоение и очистка

### Проверить тип и номер

```csharp
SfrCardInfo? info = await Task.Run(station.ReadCardInfo);
if (info is null)
    Console.WriteLine("Чип недоступен");
else if (info.Kind == SfrCardKind.Participant)
    Console.WriteLine($"Номер участника: {info.Number}");
else
    Console.WriteLine($"Тип чипа: {info.Kind}, заголовок: {info.HeaderHex}");
```

Фрагмент выполняется при отсутствии активной команды записи/очистки.
`Number` равен `null` для `Service` и `Unknown`. Номер `0` допустим и не означает
отсутствие чипа. `MarkerHex` — поле памяти, не UID. При исчезновении посередине
чтения возможен `SfrCardNotReadyException`: частичный результат не возвращается,
но соединение остаётся пригодным для следующего чтения.

### Выбрать одну операцию

```csharp
// Assign a participant number while preserving existing punches.
var assigned = await writer.AssignAsync(123, cancellationToken);

// Alternatively: clear punches and assign the requested number.
var assignedAndCleared = await writer.AssignAsync(123, cancellationToken, clearCard: true);

// Alternatively: clear punches while retaining the existing number.
var cleared = await writer.ClearAsync(cancellationToken);
```

Это три альтернативы, а не последовательность для одного нажатия кнопки.
Каждая команда ждёт чип, выполняет действие, проверяет данные, затем посылает
сигнал. Не добавляйте свой `Beep()` после успешной команды: сигнал уже входит
в неё вместе с паузой станции 300 мс.

Новый номер — `0–39999`. Текущий номер сообщать не нужно: DLL сама проверяет чип.
Если все четыре байта номера уже соответствуют запросу, лишняя запись
не отправляется, но чтение и сигнал остаются.

Служебный чип при любой команде присвоения или очистки преобразуется в обычный
с очисткой памяти, независимо от `clearCard`. Лёгкого режима «снять служебный
заголовок без очистки» нет. При отдельной очистке служебного чипа сохраняется
корректный номер `0–39999`, иначе устанавливается `0`. Номер обычного чипа при
отдельной очистке сохраняется полностью, включая старший байт формата.
Неизвестный заголовок по умолчанию обрабатывается так же: выполняется полная
очистка поддерживаемого диапазона и приведение к обычному формату. При отдельной
очистке сохраняется корректный номер 0–39999, иначе устанавливается 0.
При присвоении записывается запрошенный номер. Старые отметки стираются даже
при `clearCard: false`; результат сообщает `CardCleared = true`.
Для прежнего запрета установите `FormatUnknownCards = false` при открытии:
тогда неизвестный заголовок вызывает `SfrProtectedCardException` до записи.

Обычный заголовок может содержать ненулевые дополнительные байты, например
`06 00 F0 00`: это не служебный режим. Запись без очистки сохраняет его полностью.
При полной очистке он сбрасывается в `05 00 00 00`.

### Выбрать режим очистки

По умолчанию используется `AfterEachWrite`. Для прежней полной итоговой проверки
передайте при открытии `new SfrStationOptions { ClearMode = SfrClearMode.FullMemory }`.
Настройка действует на отдельную очистку, присвоение с `clearCard: true` и
автоматическое преобразование служебного/неизвестного чипа. Она сама по себе
не включает очистку обычного чипа при записи номера.

Все режимы сначала читают всю поддерживаемую память 02–7F и находят непустые
ячейки, включая старые отметки за счётчиком. Записываются только необходимые
изменения. Число в заголовке не используется для сокращения диапазона.

| Режим | Проверка |
|---|---|
| `AfterEachWrite` (по умолчанию) | Каждая записанная ячейка немедленно читается и сравнивается. Следующая запись отправляется только после подтверждения. В конце проверяются номер, тип и маркер |
| `FullMemory` | После записей проверяется весь диапазон 02–7F, затем номер, тип и маркер |
| `ThroughLastNonEmptyCell` | После записей проверяется диапазон 02–последняя непустая ячейка, минимум до 05, затем номер, тип и маркер. Для служебных/неизвестных чипов применяется `FullMemory` |

После `2A 08` текущая ячейка проверяется до продолжения во всех режимах.
В двух режимах с итоговым проходом ответ `2A 55` допускает переход к следующей
записи без немедленного чтения данных; исключение — заголовок 04, проверяемый сразу.

Если чип исчез во время немедленной проверки, DLL ждёт его возврата согласно
`VerificationReturnTimeoutMs`, сверяет маркер и заголовок и повторяет только
чтение. Запись не повторяется. Несовпадение данных или исчерпание ожидания даёт
`Success = false`, без перехода к следующей записи и без сигнала успеха.
При потере чипа подготовка повторяется целиком; итоговая проверка повторяется
целиком в пределах выбранного режима.

`AfterEachWrite` не обнаружит изменение уже проверенной ячейки во время более
поздних записей или появление данных в ранее пустом хвосте. `FullMemory`
дополнительно проверяет эти случаи. Поэтому режимы не полностью эквивалентны
по надёжности. Выигрыш по числу обменов больше на почти пустых чипах;
при заполненной памяти почти каждую ячейку всё равно нужно прочитать после записи.

## 4. Обработка результата

```csharp
static string DescribeResult(SfrNumberAssignmentResult result)
{
    if (result.Success)
    {
        var text = $"Номер {result.Card.Number} подтверждён";
        if (result.CardCleared) text += ", отметки очищены";
        if (!result.SignalSent) text += $". Сигнал не отправлен: {result.SignalError}";
        return text;
    }

    var message = result.CardMayHaveChanged
        ? $"Результат не подтверждён; данные могли измениться. {result.Error}"
        : $"Чип не изменён. {result.Error}";
    return result.RequiresReconnect ? message + " Переподключите станцию." : message;
}
```

| Поле | Как использовать |
|---|---|
| `Success` | Данные подтверждены; только после этого фиксируйте успешное присвоение в своей программе |
| `Card` | Проверенные `Number` и `MarkerHex`; при неудаче `null` |
| `CardCleared` | Очистка выполнена и проверена, включая перевод служебного/неизвестного чипа |
| `ClearedThroughCell` | Граница охваченного очисткой диапазона: `0x7F` для `AfterEachWrite`/`FullMemory`, найденная граница для `ThroughLastNonEmptyCell`; `null` без подтверждённой очистки. Момент проверки зависит от `AppliedClearMode` |
| `AppliedClearMode` | Фактически применённый режим успешной очистки; `null` без подтверждённой очистки. В `AfterEachWrite` пустые ячейки проверены при подготовке, изменённые — сразу после записи |
| `SignalSent`, `SignalError` | Удалось ли отправить сигнал; его сбой не отменяет подтверждённую запись |
| `Failure`, `Error` | Категория неудачного результата и текст причины; решение в коде принимайте по полям, не по тексту |
| `CardMayHaveChanged` | При `Success = false`: была попытка изменения, данные могли измениться полностью или частично |
| `RequiresReconnect` | Соединение нужно закрыть и открыть заново до следующего обращения |
| `RequestedNumber` | Запрошенный номер в неудачном результате; `null` при отдельной очистке |
| `LastAttemptedCell` | Последняя ячейка, запись которой пытались выполнить; не гарантирует её изменение, `null` до записи |

| `Failure` | Что произошло | Действие приложения |
|---|---|---|
| `PreparationFailed` | Подготовка очистки не завершилась до первой записи | Чип не изменён, соединение открыто; оператор может повторно запустить команду |
| `WriteUnverified` | Попытка записи номера была, проверка не подтверждена | Не записывать автоматически снова; вернуть чип и прочитать номер |
| `ClearUnverified` | Многоячеечная операция могла выполниться частично | Не считать чип очищенным; проверить его перед новой командой |

Для двух последних строк необходимость переподключения определяется
`RequiresReconnect`, а не названием результата. Ответ `2A 06` при поддерживаемой
подготовке/проверке и несовпадение проверяемых данных возвращают обычную неудачу
без разрыва соединения. Тайм-ауты, повреждённые ответы и некоторые другие сбои
между записями при очистке блокируют обмен — смотрите флаг.
`Success = true, SignalSent = false` всё равно является подтверждённой записью.
`CardMayHaveChanged` предназначен для ветки неудачи, а не для определения,
производилась ли физическая запись при успешной команде.

### Исключения, которые остаются в API

Ожидаемые неподтверждённые изменения возвращаются результатом. Но асинхронные
методы всё ещё могут выбрасывать исключения:

| Исключение | Когда | Что делать |
|---|---|---|
| `OperationCanceledException` | Отмена до первой попытки изменения | Завершить ожидание без сообщения об аварии |
| `SfrProtectedCardException` | Неизвестный заголовок при `FormatUnknownCards = false` | Показать причину и `HeaderHex`; соединение пригодно для работы |
| `ArgumentOutOfRangeException` | Неверный номер или настройки | Проверить ввод до запуска команды |
| `InvalidOperationException` | Параллельный запуск, недопустимое состояние, несовпадение ожидаемого номера | Исправить управление командами; после ранее отмеченного сбоя переподключиться |
| `IOException`, `TimeoutException` | Ошибка открытия/обмена до изменения | Закончить задачу, сохранить диагностику и заново открыть соединение |
| `NotSupportedException`, `PlatformNotSupportedException` | Неизвестный дескриптор или неподдерживаемая ОС | Проверить оборудование и среду |

`SfrProtectedCardException` и `SfrCardNotReadyException` наследуют `IOException`:
обрабатывайте их раньше общего обработчика ввода-вывода. После попытки записи
ошибки обмена обычно преобразуются в результат с `RequiresReconnect = true`.

## 5. Отмена и последовательность чипов

Для кнопки отмены храните `CancellationTokenSource` текущей команды и вызывайте
`Cancel()`. Пока запись не началась, отмена прекращает ожидание/подготовку.
После первой попытки изменения DLL заканчивает проверку и возвращает фактический
результат, даже если токен отменён. Токен на 30 секунд не является жёстким
ограничением длительности всей операции.

При серии чипов передавайте `waitForRemoval: true`, если предыдущая попытка уже
могла изменить чип, а его снятие ещё не было замечено. Команда дождётся двух
последовательных ответов об отсутствии и затем будет искать следующий чип.

```csharp
bool requireRemoval = false;
foreach (int number in new[] { 101, 102, 103 })
{
    var result = await writer.AssignAsync(number, cancellationToken,
        waitForRemoval: requireRemoval);
    requireRemoval = result.Success || result.CardMayHaveChanged;
    if (!result.Success)
    {
        Console.WriteLine(result.Error);
        break; // Do not advance to the next participant after a failed assignment.
    }
    Console.WriteLine($"Готово: {result.Card.Number}. Уберите чип.");
}
```

Сам writer не запоминает обязанность снять предыдущий чип между вызовами — это
состояние хранит приложение. WPF-пример реализует его в
[`CardPresence.cs`](../SfrConnect.TestApp/CardPresence.cs). Если приложение уже
подтвердило снятие фоновым чтением, флаг можно сбросить. Чип, убранный и возвращённый
между двумя опросами, не считается достоверно снятым.

## 6. WPF и жизненный цикл

1. Найти/открыть станцию через `Task.Run`, сохранить соединение и один writer.
2. При нажатии «Записать» зафиксировать номер и флаг очистки, остановить опрос
   и дождаться уже начатого чтения. Не допускать второго запуска команды.
3. Создать `CancellationTokenSource` и `Progress<SfrAssignmentStage>` в UI-потоке,
   затем вызвать `await writer.AssignAsync(...)`.
4. Обработать результат, обновить участника только при подтверждённом успехе.
5. Возобновить опрос, если соединение пригодно. При `RequiresReconnect` закрыть
   его и предложить открыть заново.

| Стадия прогресса | Сообщение для оператора |
|---|---|
| `WaitingForRemoval` | Уберите предыдущий чип |
| `WaitingForCard` | Приложите чип |
| `Writing` | Запись номера и проверка; держите чип до завершения |
| `Clearing` | Очистка и проверка; держите чип до завершения |

Подробные этапы и длительность передаются через журнал. Пример короткой
операции, которая сама открывает и освобождает соединение:

```csharp
static async Task<SfrNumberAssignmentResult> AssignOnceAsync(
    string devicePath, int number, CancellationToken cancellationToken,
    IProgress<SfrAssignmentStage>? progress = null)
{
    using var station = await Task.Run(() => SfrStation.Open(devicePath));
    var writer = new SfrNumberWriter(station);
    return await writer.AssignAsync(number, cancellationToken, progress);
}
```

Для постоянного рабочего окна открывайте соединение один раз, а не на каждую
кнопку. Низкоуровневая блокировка DLL не разрешает вмешивать фоновое чтение между
шагами `AssignAsync`. Этот метод уже работает в фоне: дополнительный `Task.Run`
вокруг него не нужен.

При закрытии окна остановите таймер опроса, отмените ожидание и **асинхронно
дождитесь** текущей задачи. Только затем `Dispose()` станции и закрытие окна.
Не используйте `.Wait()`/`.Result` в UI-потоке. Нельзя освобождать HID-поток,
пока проверяется возможная запись.

Рабочие примеры:

- [`MainWindow.xaml.cs`](../SfrConnect.TestApp/MainWindow.xaml.cs): команды, отмена,
  обработка результата и закрытие окна.
- [`StationOperations.cs`](../SfrConnect.TestApp/StationOperations.cs): очередь
  опроса и команд без пересечения операций.
- [`ExchangeLog.cs`](../SfrConnect.TestApp/ExchangeLog.cs): потокобезопасный буфер журнала.

## 7. Журнал и замеры

Передайте `log: message => ...` в `SfrStation.Open`. Callback может вызываться
из рабочего потока. Он должен быстро добавлять строку в очередь, не обращаться
напрямую к WPF-контролам и не выбрасывать исключений.

Строки `ЭТАП · ` содержат начало, завершение/прерывание и длительность этапа.
«ВСЯ КОМАНДА» включает ожидание и сигнал; не складывайте его с отдельными этапами.
TX/RX нужны для разбора обмена, а не для определения успеха в программе — для
этого служит `SfrNumberAssignmentResult`.

В тестовом окне журналы ограничены 500 сообщениями и обновляются раз в 250 мс;
у текстовых полей отключена история отмены. Используйте аналогичный буфер,
чтобы поток пакетов не перегружал интерфейс.

## 8. Низкоуровневый API и ограничения

`ReadCardNumber`, `ReadCardInfo`, `WriteCardNumber`, `ClearCard`, `Beep` —
синхронные методы. `WriteCardNumber`/`ClearCard` не ждут первичного появления
чипа и не подают сигнал автоматически. Их контракт при неудаче основан на
исключениях, в отличие от рекомендуемых асинхронных команд.

| Метод/исключение | Особенность |
|---|---|
| `WriteCardNumber(newNumber)` | Номер читается перед изменением автоматически |
| `WriteCardNumber(expectedCurrentNumber, newNumber)` | При другом текущем номере запись не начинается |
| `WriteCardNumber(newNumber, clearCard: true)` | Синхронная очистка и присвоение |
| `SfrWriteUnverifiedException` | Номер мог измениться; открыть соединение заново и проверить |
| `SfrCardUpdateUnverifiedException` | Очистка могла выполниться частично; открыть соединение заново и проверить |
| `SfrCardNotReadyException` | Чип исчез/изменился до записи; соединение не заблокировано |

Очистка поддерживает 128 ячеек и не является атомарной. Отката частичной операции
нет. В библиотеке нет чтения полного результата дистанции, базы участников,
автоматического увеличения номера или API программирования служебных режимов.
Приложение формирует следующий номер и решает, кому его присвоить.
Ограничения и происхождение формата описаны в [справочнике протокола](protocol.md).

`FormatUnknownCards` разрешает преобразование неизвестного содержимого заголовка,
но не расширяет поддержку оборудования: защищённая от записи память, неисправный
чип, другой размер памяти и повреждённые ответы всё ещё могут завершить операцию
неудачей. Проверки памяти и чтение после записи остаются обязательными.
